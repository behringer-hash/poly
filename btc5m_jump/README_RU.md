# btc5m_maker: мейкерское исполнение сигнала C1

Отдельный проект на основе btc5m_lab. Сигнал тот же, что у C1: порог 3,5 ц, sigma ×1, Bybit. Меняется исполнение:
бот не покупает тейкером, а ставит **пассивную лимитную заявку на покупку** и через 2 секунды снимает её.
Бумажной торговли нет, есть только сигнал и заявки.

## Почему так

Разбор на данных 10–21 октября (задания M1, M2 и M4 в репозитории btc5m_lab) показал:

- Бумажная прибыль C1 почти целиком получается за счёт покупки по устаревшей цене. Тейкером её не забрать: биржа держит
  каждый тейкерский ордер 150 мс, и к матчингу котировка уже переоценена.
- Пассивная заявка этой задержки не проходит и встаёт в книгу примерно за 25 мс. Сразу после скачка BTC в лучший bid по старой
  цене бьют запоздавшие продажи, отправленные ещё до скачка.
- Исполнения в первые 0,5 с дают около +13 ц на шейр, поздние исполнения убыточны. Поэтому заявка живёт недолго.
- В симуляции это около +0,5…+0,9 ц на сигнал. Результат держится, пока задержка постановки не больше 100 мс,
  и почти исчезает при 400 мс.
- Порог сигнала ниже 3–3,5 ц прибыли в день не прибавляет, а при строгом подсчёте сделок её уменьшает (задание M7).
- Заявка по ask в симуляции даёт +2,4 ц на сигнал против +1,0 ц у bid+1, но около 80% этого — исполнение сразу
  тейкером, которое симуляция завышает: в живых запусках C1 такие покупки давали гораздо меньше. Поэтому режим
  `ab` сравнивает оба способа на живых заявках.

## Как работает

1. Приходит сигнал C1. Цена заявки зависит от режима `maker_price`:
   - `improve` — лучший bid стороны сигнала, или bid + 1 ц, если спред не меньше 2 ц. Заявка post-only: если она
     пересекла бы спред, сервер её отклонит, поэтому тейкером бот не покупает;
   - `ask` — цена равна ask в момент сигнала, без post-only. Если ask ещё стоит, когда заявка доходит до биржи, она
     исполняется сразу как тейкерская: биржа держит её 150 мс, берётся комиссия тейкера. Если ask уже ушёл, заявка
     остаётся в книге bid'ом по этой цене до снятия;
   - `ab` (по умолчанию в конфигах) — **A/B-тест**: на каждый сигнал случайно, 50 на 50, выбирается `improve` или `ask`
     (список в `ab_modes`). Оба режима проверяются в одинаковых условиях, итоги считаются раздельно.
2. Тип заявки GTD со сроком 90 с: если бот упадёт, биржа сама снимет заявку по истечении срока.
3. Через `maker_life_sec` (2 с) бот снимает заявку и запрашивает у биржи, сколько исполнилось.
4. Купленное держится до конца окна. Мейкер комиссию не платит, тейкер (исполнение сразу по ask) платит 0,07·p·(1−p).
5. Бот всегда считает исполнение по сделкам рынка: заявка встаёт в конец очереди своего уровня. В режимах dry и sign
   учёт ведётся по нему, в live оно пишется рядом с фактическим исполнением для сравнения.

## Что видно в консоли

На каждый сигнал выводятся две строки, через 2 с — итог заявки, а после закрытия окна — результат каждой исполненной заявки:

10:41:05.840 ИТОГ   #12 [bid+1] Up @ 0.49: ИСПОЛНЕНА 5 шт по сделкам рынка, первое через 180 мс, полностью через 180 мс

══ ОКНО 10:40-10:45 закрыто, победил Up | заявок 9, исполнено 2 (по сделкам рынка)

Если заявка не ставится (лимит, нет цены ниже ask, мало времени до конца окна), вместо строки ЗАЯВКА бот пишет
`СИГНАЛ #N ... - заявка не ставится: причина`. Раз в 10 минут выводится служебная строка `[pm]` о связи и задержках.

## Файлы

| файл | что это |

| `maker_bot.py` | запуск бота: сигнал и лимитные заявки |

| `report.py` | сводка теста по папке данных |
| `tests/` | проверки (`python3 -m pytest -q tests`) |

## Установка

**С нуля:**

```bash
cd ~ && unzip btc5m_maker_v3.zip                 # создаст папку ~/btc5m_maker
cd ~/btc5m_maker && chmod +x run_*.sh
pip3 install -r requirements.txt --break-system-packages
python3 -m pytest -q tests                        # должно быть: 32 passed
nano config_sign_test.json                        # вписать funder, проверить signature_type (у вас 3)
```

**Поверх прошлой версии, без перезаписи ваших настроек:**

```bash
cd ~ && unzip -o btc5m_maker_v3.zip -x "btc5m_maker/config_sign_test.json" "btc5m_maker/config_live*.json"
cd ~/btc5m_maker && rm -f bot.py maker.py tests/test_live_paper_params.py && chmod +x run_*.sh
python3 -m pytest -q tests                        # 32 passed
```

Ключи `signal_edge`, `signal_source` и `signal_sigma_mult` в старом конфиге не обязательны: по умолчанию это 0,035,
Bybit и 1. Чтобы включить A/B-тест в старом конфиге, достаточно поменять одну строку: `"maker_price": "ab"`
(`ab_modes` по умолчанию `["improve", "ask"]`).

## Тест в режиме sign (заявки подписываются, но НЕ отправляются)

```bash
tmux new -s mk                    # если пишет «duplicate session»: tmux kill-session -t mk, затем снова
./run_sign.sh                     # спросит приватный ключ (не отображается и не сохраняется)
# отключиться, оставив работать: Ctrl+B, затем D (латинская); вернуться: tmux attach -t mk
```

Лимиты на количество заявок, на окно, на сутки и на весь запуск сняты. По каждому сигналу ставится своя заявка,
даже если прошлая на той же стороне ещё стоит. Остались только защиты, не связанные с количеством:
- не ставить заявки позже чем за 10 с до конца окна;
- диапазон цен 0,05–0,95;
- остановка после 5 ошибок подписи подряд;
- файл `STOP`.

Что проверить:

1. При старте — баланс по типам подписи. Если бот предлагает другой `signature_type`, исправьте его в конфиге.
   При балансе меньше $5 бот всё равно предупредит о нём; для sign это неважно.
2. В строках ЗАЯВКА большинство подписей должно быть готовыми («готовая подпись»).
3. В строке ОКНО растёт «сделок рынка получено». Если там 0, исполнение по сделкам рынка не работает.
4. Через сутки запустите `python3 report.py data_sign`. Ориентиры симуляции:
   - исполнено около 10–12% заявок;
   - результат +0,5…+0,9 ц на шейр заявки;
   - большая часть прибыли приходится на исполнения в первые 0,5 с.

Остановка: `touch STOP` в папке проекта, затем Ctrl+C.

## Режим live (после sign, отдельно)

```bash
cp config_live.example.json config_live.json && nano config_live.json   # funder, signature_type, лимиты
./run_live.sh                     # попросит ключ и ввести «ДА»
```

В первые минуты проверьте:
- заявки принимаются. Если сервер отклоняет их из-за срока действия, поставьте `"order_type": "GTC"`;
- в строках ЗАЯВКА «ответ биржи» укладывается в 20–50 мс;
- в строках ИТОГ видно снятие (`canceled`).

Выигрыши бот не забирает: Claim делается вручную. При полном потоке сигналов это около 100 исполнений в сутки
по ~$2,5, поэтому баланса должно хватать до ближайшего Claim.

**Критерии живого теста (зафиксированы заранее):**
- размер 5 шейров, примерно 3 суток;
- сравнить с симуляцией долю исполнений, результат на сигнал, время исполнения и фактическое исполнение
  против исполнения по сделкам рынка;
- остановить и разобраться, если доля исполнений меньше 5% или после 300 исполнений результат на исполнение
  ниже нуля с учётом погрешности.

## Что пишется (папка `data_*`)

| поток | содержимое |
|---|---|
| `paper_signals` | каждый сигнал: время, сторона, ask/bid, справедливая цена, edge, ход BTC, время до конца окна |
| `maker_orders` | каждая заявка: время сигнала, отправки и ответа, цена, размер, статус, номер, bid/ask, очередь, время подписи |
| `maker_final` | итог заявки: снятие, `size_matched` по бирже, исполнение по сделкам рынка (шт, время первого и полного) |
| `maker_user_events` | события приватного канала по своим заявкам (только live) |
| `live_windows` | итог окна, в live со сверкой с Polymarket |
