# BTC 5m lab — сбор данных, проверка гипотез, бумажная торговля

Программа собирает синхронизированные данные по 5-минутным BTC-рынкам Polymarket, Binance и кошельку, который мы изучаем, и параллельно ведёт бумажную торговлю по гипотезе «покупка устаревшего ask после тика BTC». Реальных ордеров она **не отправляет**, ключи и кошелёк ей не нужны.

## Установка (Windows 11)

1. Python 3.12 или новее (3.13 предпочтительнее: у него точные системные часы на Windows, хотя программа учитывает это и сама).
2. В папке программы выполнить:
   ```
   pip install -r requirements.txt
   ```
3. Синхронизация часов (желательно, от имени администратора в PowerShell):
   ```
   w32tm /config /manualpeerlist:"time.google.com,0x9 pool.ntp.org,0x9" /syncfromflags:manual /update
   reg add HKLM\SYSTEM\CurrentControlSet\Services\W32Time\TimeProviders\NtpClient /v SpecialPollInterval /t REG_DWORD /d 64 /f
   net stop w32time
   net start w32time
   w32tm /resync
   ```
   Программа раз в минуту сама измеряет смещение ваших часов относительно сервера Binance и записывает его, поэтому анализ всё равно будет корректным. Хорошая синхронизация просто уменьшает погрешность.
4. Отключите сон и гибернацию на время сбора. Папку `data` желательно добавить в исключения антивируса.

## Запуск

```
python run.py
```
или двойной щелчок по `start.bat`. Остановка — Ctrl+C: данные сбрасываются на диск каждые 2 секунды, так что при остановке ничего существенного не теряется.

Полезные ключи:

| ключ | что делает |
|---|---|
| `--no-paper` | только сбор данных, без бумажной торговли |
| `--latencies 50,150,300,600` | задержки ордера для бумажной торговли, мс |
| `--binance-ws wss://data-stream.binance.vision` | другой адрес Binance (также `wss://stream.binance.com:443`) |
| `--binance-streams aggTrade,depth5` | какие потоки Binance брать: `aggTrade`, `bookTicker`, `depth5` |
| `--paper-btc-source bybit` | основной источник цены BTC для бумажной торговли: `bybit` (по умолчанию), `coinbase`, `binance`, `rtds`. Bybit и Coinbase подключаются всегда |
| `--no-coinbase` | не подключать Coinbase |
| `--extra-feeds binance_futures,bybit` | доп. биржи для записи: `binance_futures`, `bybit`, `okx` (`none` — отключить) |
| `--only pm` | запустить только часть процессов: `cex`, `pm`, `wallet` |
| `--data-dir D:\lab\data` | куда писать данные |

## Запись данных для поиска опережающих индикаторов

`python3 run.py --no-paper --extra-feeds all` дополнительно пишет: верх книги фьючерса Binance с объёмами (`bnf_book`), 5 уровней книги фьючерса раз в 100 мс (`bnf_depth5`), ликвидации Binance и Bybit (`bnf_liq`, `by_liq`), верх книги Bybit с объёмами (`by_book1`), сделки Kraken и Bitstamp (`kr_trade`, `bs_trade`). У каждого потока несколько адресов: если по одному нет данных, программа переходит к следующему. Объём данных заметно больше обычного (сотни сообщений в секунду).

## Варианты по дисбалансу книги

`imb90_p1..p3`, `imb95_p1..p3` — покупка стороны, когда дисбаланс верха книги фьючерса Binance (bid_qty − ask_qty)/(bid_qty + ask_qty) достигает 0,90 / 0,95 в её пользу; `imb90_m1_p1..p3` — то же, плюс подтверждение ходом цены фьючерса за 150 мс не меньше 1σ. Окончание `_p1/_p2/_p3` — лимит ask + 1/2/3 ц; цены 0,10–0,90. Нужен ключ `--binance-fut-book` (и `--binance-fut` для `imb90_m1_*`).

## Моментум-варианты

`mom2_bnf`, `mom4_bnf` (фьючерс Binance, ход $2 / $4 за 300 мс), `mom2_bn` (спот Binance), `mom2_bnany` (что раньше: спот или фьючерс). Сигнал — ход цены источника за 300 мс больше порога; покупается сторона по направлению хода, лимит = ask + 1 ц, без проверки справедливой цены. Нужны ключи `--binance-fut` (фьючерс) и/или `--binance-source` (спот).

`mom25s`, `mom35s` — порог от волатильности: k × (волатильность фьючерса за последние 5 минут) × √0,3 с, k = 2,5 и 3,5; цены 0,30–0,95. `mom4_bnf30` — фиксированные $4 в том же диапазоне цен, для сравнения.

## Бумажный бот отдельно: `bot.py`

`python bot.py` (или `start_bot.bat`) — бумажная торговля без сбора сырых данных, с подробной консолью и живым графиком текущего окна (цены Up/Down с отметками сигналов, исполнений и промахов; BTC относительно price to beat; позиция и оценка PnL окна; результат по окнам). Ордера не отправляются. Свои сделки бот пишет в `bot_data`.

| ключ | что делает |
|---|---|
| `--show anc_3c_by@150` | какой бумажный счёт показывать подробно (вариант@задержка); `all` — все |
| `--variants anc_2c_by,anc_3c_by` | торговать только этими вариантами; свой вариант: `имя:порог:источник`, например `my:0.025:both` |
| `--latencies 50,150,300,600` | задержки ордера, мс |
| `--no-chart` | только консоль |

Бот можно запускать одновременно со сборщиком `run.py` — это независимые программы. Остановка: закрыть окно графика или Ctrl+C.

## Живой тест (реальные ордера минимального размера)

Нужна библиотека Polymarket CLOB v2: `pip install py_clob_client_v2`.

1. Скопируйте `live_config.example.json` в `live_config.json` и впишите `funder` — адрес вашего кошелька Polymarket — и `signature_type` (3 — новые аккаунты, в т.ч. по email; режим `sign` сам подскажет правильный). Лимиты можно ужесточить.
2. Приватный ключ **не пишите в конфиг**. Задайте его в окне PowerShell только на время сеанса: `$env:PM_PRIVATE_KEY="0x..."`. Для аккаунтов с входом по email ключ экспортируется в настройках Polymarket.
3. Проверка по шагам:
   - `python bot.py --live live_config.json --mode dry` — без ключа, показывает, какие ордера отправил бы и какие отсёк бы по лимитам;
   - `python bot.py --live live_config.json --mode sign` — подключается с ключом, показывает баланс, подписывает ордера, но **не отправляет**;
   - `python bot.py --live live_config.json --mode live` — реальные ордера; перед стартом нужно ввести «ДА».
4. Аварийная остановка — создать файл `STOP` в папке программы: новые ордера перестанут отправляться. Выход — закрыть график или Ctrl+C.

Режим переплаты `slippage_mode`: `edge` — переплата равна запасу сигнала минус `edge_margin_cents` (от 0 до `edge_slip_max_cents`), то есть бот никогда не платит больше, чем стоит сигнал; `edge_scale` умножает запас по модели (модель занижает реальную ценность сигнала в 1,5–2 раза), а в последние `last_minute_sec` секунд окна действует свой потолок `edge_slip_max_last_min_cents`; `random` — случайно из `slippage_choices` (для экспериментов); `fixed` — всегда `slippage_cents`.

Параметр `slippage_cents` в конфиге: на сколько центов выше увиденного ask ставить лимит (например, 3). Ордер заберёт все уровни книги до этой цены; платится фактическая цена уровней, а не лимит.

Размер ордера по объёму на лучшем ask (`size_by_depth`, например `[[100, 10], [300, 20]]`): на толстом ask исполняемость втрое выше, поэтому там бот берёт больше, но не больше, чем стояло по цене сигнала.

Ордера на текущий ask и цены с переплатой бот подписывает заранее (`presign`), так что по сигналу отправляется готовый ордер.

Ордера — FAK (исполнить что можно и отменить остаток), поэтому в книге ничего не остаётся. Выигрыш нужно забирать (Claim) в интерфейсе Polymarket, бот этого не делает. Все живые ордера пишутся в `bot_data` (`live_orders`, `live_windows`) с номером бумажного сигнала для сравнения.

## Запуск на сервере (Linux, например AWS Lightsail в Стокгольме)

Нужен сервер минимум с 1 ГБ памяти (лучше 2 ГБ) или файл подкачки. Установка: `sudo apt install -y python3-pip unzip tmux`, затем `pip3 install websockets orjson requests pandas py_clob_client_v2 --break-system-packages`. Запускать внутри `tmux`, без графика: `python3 bot.py --live live_config.json --mode live --no-chart --clip 5 --single-clob`. В строке статуса бот показывает `память` и `loop p99` — если последний уходит в сотни мс, серверу не хватает процессора.

## Тест задержек ордеров: `order_latency_test.py`

Раскладывает время ордера на части: сеть, авторизация, постановка ордера без исполнения и его отмена, исполняемые FAK (с `defer_exec` и без) и лимитный GTC. Серверное время исполнения берётся из потока сделок по хэшу транзакции, параллельно пишутся события приватного канала. Запуск при остановленном боте: `python3 order_latency_test.py --config live_config_mm.json` (или `--no-fill` — только бесплатные тесты). Итог — таблица и файл `order_latency_<время>.json`.

## Выбор сервера (VPS): `latency_probe.py`

Один самостоятельный файл: `pip install websockets requests numpy`, затем `python latency_probe.py` (10 минут). Проверяет, разрешена ли торговля с этого IP, меряет путь ордера до Polymarket, задержку книги и сделок Polymarket и задержку BTC со всех бирж. В конце печатает сводку и сохраняет `probe_<имя>_<время>.json`.

## Если Binance приходит с задержкой

По умолчанию Binance берётся с `data-stream.binance.vision` потоками `aggTrade,depth5`, а бумажная торговля использует Coinbase: по вашему тесту это самые быстрые варианты.

`python bn_diag.py` за ~3 минуты проверит разные адреса, порты и наборы потоков Binance и покажет, какой вариант работает у вас без задержек. Выбранный вариант задаётся ключами `--binance-ws` и `--binance-streams`.

`python net_check.py` (~30 секунд) покажет системный прокси, время TCP/TLS-соединения до каждой биржи и кто выдал TLS-сертификат. Если сертификат выдан антивирусом или прокси, а не публичным центром сертификации, трафик расшифровывается по дороге. Это частая причина задержек.

## Из чего состоит программа

Три независимых процесса. Упавший процесс перезапускается автоматически.

- **cex** — сырые Binance (`aggTrade` — все сделки с биржевым временем в мс, `bookTicker` — лучшие цены) и Coinbase. Также раз в минуту измеряет смещение часов. Процесс отдельный, чтобы тяжёлый поток Polymarket (~1000 сообщений/с) не мог задержать приём BTC.
- **pm** — книга Polymarket (одно соединение на окно: в каждом сообщении приходят обе стороны), все сделки рынка с `transaction_hash`, Chainlink/TWAP60 через RTDS, определение исхода окна, бумажная торговля.
- **wallet** — действия кошелька через data-api: TRADE, REDEEM, MERGE, SPLIT, CONVERSION.

Выделять и копировать текст в консоли можно как обычно: вывод идёт через отдельный поток, и выделение мышью не останавливает сбор данных.

Раз в 10 секунд каждый процесс печатает статус: задержки фидов, число сообщений и `lag loop`. Последний показывает, не перегружен ли процесс; нормально, когда он в пределах нескольких мс.

## Файлы данных

`data/<дата UTC>/<поток>_<час UTC>.csv.xz`. Текущий час пишется обычным `.csv` и сжимается в `.xz` при смене часа и при остановке программы; незакрытые файлы после сбоя сжимаются при следующем запуске. Открыть `.xz` можно 7-Zip. Все времена — целые миллисекунды (`recv_ms` — локальное время приёма).

| поток | содержимое | гипотеза |
|---|---|---|
| `bn_agg` | все сделки Binance, `E`/`T` — время биржи (мс) | задержка фида, моменты тиков |
| `bn_book` | лучшие цены Binance при каждом изменении | |
| `cb_ticker` | Coinbase BTC-USD | какая биржа ведёт |
| `bnf_agg` | сделки фьючерса Binance BTCUSDT (бессрочный), `T` — время биржи | триггер «тихих» входов кошелька |
| `by_trade`, `ok_trade` | сделки бессрочных BTC-USDT на Bybit и OKX (у OKX размер в контрактах по 0,01 BTC) | то же |
| `health_feeds` | задержка и число сделок доп. бирж за 10 с | качество данных |
| `clock`, `clock_pm` | смещение часов относительно Binance | коррекция времени |
| `pm_top` | каждое изменение лучших цен Up/Down (с объёмами на них); для Up — также изменения объёма на лучших ценах, не чаще раза в 50 мс (книга Down — зеркало Up); `d` — задержка от сервера Polymarket | устаревшие ask, истончение уровней |
| `pm_depth` | топ-5 уровней книги, 2 раза в секунду | дисбаланс книги |
| `pm_trades` | все сделки рынка: сторона, цена, размер, первые 16 символов хэша транзакции, время сервера | точное время сделок кошелька |
| `pm_rtt` | время HTTPS-запросов к серверу CLOB, включая пустой запрос к `/order` (без ключей, отклоняется) | задержка ордера |
| `rtds` | Chainlink, TWAP60, Binance через Polymarket | резолюция, базис |
| `windows` | окна: токены, price to beat, предварительный и официальный исход | |
| `wallet` | действия кошелька (`seeded=1` — история до запуска) | |
| `paper_*` | сигналы, исполнения, маркауты, итоги окон | бумажная торговля |
| `health_*` | задержки, нагрузка | качество данных |

Ориентировочный объём — около 35 МБ в сутки (без изменений объёма, ключ `--top-sizes none`, — около 25 МБ).

К каждому окну открываются **два** соединения с книгой Polymarket. Сервер иногда обрывает соединение с формулировкой «slow consumer»; тогда программа мгновенно переключается на второе, а первое переподключается в фоне. Переключения видны в `events_pm`.

## Бумажная торговля

Каждый вариант стратегии × каждая задержка ордера — отдельный бумажный счёт.

- **Модель `anchor`**: берём текущий mid стороны и сдвигаем его на ход BTC (Binance) с момента, когда этот mid последний раз менялся. Если рынок ещё не отреагировал на тик, справедливая цена уходит от ask.
- **Модель `abs`**: абсолютная вероятность того, что TWAP60 Chainlink в конце окна окажется не ниже price to beat, с учётом уже накопленной части TWAP в последнюю минуту. Это диагностический вариант.
- **Сигнал**: справедливая цена − ask − комиссия 0,07·p·(1−p) > порог. Варианты по умолчанию: `anc_1c_by`, `anc_2c_by`, `anc_3c_by` (ход цены по Bybit, порог 1/2/3 ц), `anc_3c_by_s075` и `anc_3c_by_s15` (то же с волатильностью ×0,75 — мягче и ×1,5 — строже), `anc_3c_any_s15` (строгий сигнал по первому пришедшему тику любой биржи; Binance подключается ключом `--binance-source`), `anc_3c_by_res` и `anc_2c_by_res` (исправленный якорь: при изменении книги якорь сдвигается только на ту часть хода BTC, которую книга отыграла, и неотыгранный ход не теряется), `anc_2c_cb` (по Coinbase), `anc_2c_both` (ход должны подтвердить и Bybit, и Coinbase; берётся меньший из двух).
- **Исполнение**: «купить до 50 шейров не дороже увиденного ask». Через L мс проверяется книга. Если ask ещё там, исполняемся по уровням книги, иначе засчитывается промах. Остаток ордера в книге не стоит.
- **Итог окна**: сразу после конца окна по TWAP60 (конец против начала). Официальный исход из gamma записывается в `windows` для анализа.

Варианты и параметры настраиваются в `config.py` (`variants`, `latencies_ms`, `price_lo/hi` и др.).

**Важно.** Бумажное исполнение оптимистично: оно не учитывает, что вы сами меняете книгу своим ордером, и что на тот же ask в ту же миллисекунду могут претендовать другие. Задержки 150–600 мс — более реалистичная оценка для домашнего компьютера, 50 мс — нижняя граница.

## Перед отправкой данных

```
python check_data.py
```
Скрипт покажет, сколько данных собрано, какие задержки, найдены ли сделки кошелька в потоке рынка и итоги бумажной торговли. Затем заархивируйте папку `data` целиком. Для анализа нужно минимум 1–2 суток непрерывной работы, лучше неделя.
